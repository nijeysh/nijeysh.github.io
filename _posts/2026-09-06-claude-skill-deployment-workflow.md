회사에서 Claude를 지원해주면서 업무에 AI를 조금씩 사용해보기 시작했다.

처음에는 단순히 코드를 물어보거나, 에러 로그를 던져보고, 문서 정리를 부탁하는 정도로 사용했다.  
그러다 Claude를 쓰다 보니 `Skill`이라는 개념을 알게 됐다.

처음에는 그냥 "자주 쓰는 프롬프트를 저장해두는 건가?" 정도로 생각했다.  
그런데 실제로 써보니 단순한 프롬프트 저장보다는, 반복되는 작업의 순서와 판단 기준을 정리해두는 것에 더 가까웠다.

특히 내가 가장 먼저 Skill로 만들어보고 싶었던 건 서버 배포 흐름이었다.

---

## 왜 Skill을 만들려고 했는가

내가 Claude에게 자주 하던 요청 중 하나가 있었다.

```text
서버 로컬에 띄워줘
서버 배포해줘
로컬에서 실행해줘
```

사람 입장에서는 꽤 자연스러운 말이다.  
하지만 실제로 이 한 문장 안에는 생각보다 많은 작업이 들어있다.

```text
서버 배포해
  -> 현재 상태 확인
  -> 빌드
  -> 실행
  -> 대기
  -> 로그 확인
  -> 헬스체크
  -> 성공/실패 판단
```

문제는 Claude가 이 흐름을 매번 같은 방식으로 수행하지는 않았다는 점이다.

어떤 때는 바로 빌드를 실행했고, 어떤 때는 테스트를 먼저 돌렸다.  
어떤 때는 서버 실행 명령을 다르게 사용했고, 어떤 때는 서버가 떠 있는지만 보고 끝냈다.  
헬스체크까지 확인하는 경우도 있었지만, 로그만 보고 완료됐다고 판단하는 경우도 있었다.

명령어 자체도 매번 조금씩 달랐다.  
내가 기대한 건 "배포"라는 하나의 작업 흐름이었는데, 실제로는 그때그때 Claude가 추측해서 움직이는 느낌이 있었다.

---

## 시간이 뒤죽박죽이었다

가장 마음에 들지 않았던 건 소요 시간이 매번 달랐다는 점이다.

빌드가 금방 끝나는 경우도 있었고, 생각보다 오래 걸리는 경우도 있었다.  
여기까지는 자연스러운 일이다. 변경 범위나 캐시 상태에 따라 빌드 시간은 달라질 수 있으니까.

그런데 문제는 실패했을 때였다.

이미 빌드가 실패했거나 서버가 정상적으로 뜨지 않은 상황인데도, Claude가 계속 확인하겠다며 작업을 이어가는 경우가 있었다.  
어떤 때는 10분 이상, 길게는 20분 가까이 혼자 붙잡고 있던 적도 있었다.

물론 문제를 해결하려는 시도 자체가 나쁜 것은 아니다.  
하지만 내 입장에서는 지금 어떤 상태인지 알기 어렵고, 언제까지 기다려야 하는지도 애매했다.

조금 더 기다리면 되는 상황인지, 이미 실패한 상황인지, 다시 명령을 실행해야 하는 상황인지 기준이 없었다.  
그래서 Claude가 의미 없는 재시도를 하거나, 이미 실패한 로그가 나왔는데도 계속 기다리는 일이 생겼다.

나는 이 부분을 정리하고 싶었다.

AI가 모든 걸 알아서 해주길 바란다기보다는, 최소한 내가 반복적으로 기대하는 작업은 같은 기준으로 움직였으면 했다.

---

## "배포해"는 한 문장이 아니었다

생각해보면 내가 "서버 배포해줘"라고 말했을 때 기대한 건 단순히 명령어 하나를 실행하는 게 아니었다.

내가 기대한 건 이런 흐름이었다.

```text
1. 현재 브랜치와 작업 상태를 확인한다.
2. 정해진 명령어로 빌드한다.
3. 빌드가 실패하면 로그를 확인한다.
4. 빌드가 오래 걸리면 무한정 기다리지 않는다.
5. 서버를 실행한다.
6. 서버가 뜰 때까지 일정 시간 기다린다.
7. 헬스체크를 확인한다.
8. 실패하면 서버 로그나 포트 충돌 여부를 확인한다.
9. 최종적으로 성공/실패와 확인한 내용을 정리한다.
```

이걸 매번 프롬프트로 나눠서 말하는 것도 귀찮았다.

```text
빌드 로그 확인해줘
서버 뜬 거 맞아?
헬스체크도 해봐
에러 로그 있으면 확인해줘
```

처음에는 이렇게 중간중간 내가 계속 지시했다.  
그런데 매번 같은 말을 반복하다 보니, 이건 프롬프트로 매번 말할 게 아니라 하나의 작업 기준으로 빼는 게 맞겠다는 생각이 들었다.

그래서 배포 흐름을 Skill로 정의해보기로 했다.

---

## Skill에 넣은 기준

내가 Skill에 넣고 싶었던 건 단순히 "이 명령어를 실행해라"가 아니었다.

중요한 건 명령어보다 판단 기준이었다.

예를 들면 이런 기준이다.

```text
- 배포 요청을 받으면 먼저 현재 브랜치와 작업 상태를 확인한다.
- 빌드는 정해진 명령어로 실행한다.
- 빌드와 서버 기동은 최대 5분 정도를 기준으로 기다린다.
- 5분을 넘기면 계속 기다리지 말고 현재 상태를 확인한다.
- 빌드가 실패하면 같은 명령을 반복하지 않고 실패 로그를 먼저 확인한다.
- 서버 실행 후에는 헬스체크를 수행한다.
- 헬스체크가 실패하면 서버 로그와 포트 충돌 여부를 확인한다.
- 최종적으로 성공 여부와 확인한 내용을 요약해서 알려준다.
```

특히 최대 대기 시간을 정한 게 중요했다.

이전에는 Claude가 "조금 더 확인해보겠다"며 계속 기다리는 경우가 있었다.  
그런데 배포 작업에서는 무한정 기다리는 게 답이 아닐 때가 많다.

빌드가 실패했으면 실패 로그를 봐야 하고, 서버가 뜨지 않으면 서버 로그나 포트를 봐야 한다.  
계속 기다린다고 해결되는 문제가 아닌데도 기다리고 있으면, 결국 시간만 지나간다.

그래서 일정 시간이 지나면 멈추고, 상태를 확인하고, 나에게 알려주도록 기준을 잡았다.

---

## 적용하고 달라진 점

Skill을 적용하고 나서 가장 크게 달라진 건 작업 시간이 어느 정도 예측 가능해졌다는 점이다.

이전에는 Claude에게 "배포해줘"라고 요청하면 매번 동작이 조금씩 달랐다.  
어떤 때는 금방 끝났고, 어떤 때는 실패한 상태에서도 혼자 계속 확인하겠다며 오래 붙잡고 있었다.

Skill에 기준을 넣은 뒤에는 이런 부분이 조금 나아졌다.

빌드에 실패하면 무작정 같은 명령을 반복하지 않고, 먼저 로그를 확인하고 실패 원인을 정리하도록 했다.  
서버 실행 이후에는 헬스체크를 확인하고, 정상 응답이 오지 않으면 관련 로그나 포트 상태를 확인하도록 했다.

즉, 실패했을 때 계속 오래 붙잡고 있는 게 아니라 정해진 기준 안에서 확인하고, 필요한 내용을 정리해서 알려주는 방향으로 바뀌었다.

또 하나 편했던 점은 내가 매번 여러 번 프롬프트를 나눠서 작성하지 않아도 된다는 점이었다.

예전에는 배포를 요청한 뒤에도 계속 이어서 말해야 했다.

```text
로그 확인해줘.
헬스체크도 해봐.
서버 진짜 뜬 거 맞아?
에러 있으면 정리해줘.
```

그런데 Skill에 배포 흐름을 정리해두니, 이제는 "배포해줘"라는 한마디 안에 빌드, 실행, 로그 확인, 헬스체크, 실패 분석까지 포함되었다.

이게 생각보다 편했다.  
AI가 모든 걸 완벽하게 알아서 해준다기보다는, 내가 매번 말하던 귀찮은 확인 절차를 덜 말해도 된다는 점이 좋았다.

---

## Skill은 일을 시키는 버튼이 아니었다

이번에 Skill을 만들어보면서 느낀 건, AI를 잘 쓰려면 내가 원하는 결과만 말하는 것으로는 부족하다는 점이었다.

특히 배포처럼 실패 기준과 확인 절차가 중요한 작업은 "알아서 잘 해줘"로는 부족했다.  
내가 어떤 순서로 확인하고, 어디까지 기다리고, 어떤 상황에서 멈춰야 하는지를 먼저 정리해야 했다.

Skill을 쓰고 나서 Claude가 갑자기 더 똑똑해졌다기보다는, 내가 원하는 작업 기준 안에서 움직이게 된 것에 가까웠다.

결국 Skill은 AI에게 일을 시키는 버튼이라기보다, 내가 반복 작업을 어떻게 판단하는지 문서화하는 방식에 가까웠다.

---

## 조심해야 할 점

물론 Skill에 모든 내용을 다 넣을 수는 없다.

특히 회사 서버 정보, 계정, 토큰, 인증 정보 같은 민감한 값은 Skill에 넣으면 안 된다.  
Skill에는 구체적인 비밀값보다 작업 순서와 판단 기준만 넣는 게 맞다고 생각했다.

그리고 배포는 실제 서비스 상태와 연결될 수 있기 때문에, AI에게 완전히 맡기기보다는 사람이 최종 상태를 확인하는 과정도 필요하다.

내가 Skill로 정리하고 싶었던 건 "AI가 알아서 배포를 끝내게 하는 것"이 아니라, 내가 반복적으로 하던 확인 절차를 일관되게 따라가게 만드는 것이었다.

---

## 정리

이번에 Claude Skill을 써보면서 가장 크게 느낀 건 이거다.

**AI를 더 똑똑하게 만드는 것보다, AI가 헤매지 않게 작업 범위를 정해주는 게 더 중요하다.**

나에게 "서버 배포해줘"라는 말은 한 문장이었지만, 실제로는 빌드, 실행, 대기, 로그 확인, 헬스체크, 실패 판단까지 포함된 작업이었다.

그 기준을 Skill로 정리하고 나니, Claude가 매번 다르게 움직이는 일이 줄었고, 내가 중간중간 다시 지시해야 하는 일도 줄었다.

앞으로도 블로그 작성, 코드 리뷰, 배포처럼 반복되는 작업은 이런 식으로 Skill로 분리해볼 생각이다.
