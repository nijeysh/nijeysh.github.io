최근 @Transactional 전파 속성과 JPA Flush 실행 순서를 고려하지 않고 개발하여 운영 중에 에러를 발견한 경험이 있어 다시는 이런 실수를 하지 않기 위해 정리하려고 한다.

---

## 1. 반영과 함께 발생한 에러 로그 

기존에 데이터가 있으면 삭제 후 새로 생성하고 필요 시 업데이트를 해야하는 비즈니스 로직이 있었다.  
Service A에서 Service B를 호출하고, B 안에서 또 세부적인 서비스나 메서드(C, D)를 호출하도록 개발을 진행했다.

개발 완료 후 반영하였고 추이를 확인하려고 운영 로그를 확인해보니 **SQL update 관련 에러**가 찍혔다.  
분명히 **데이터를 지우고(Delete), 새로 넣은(Insert) 다음, 그 데이터를 대상으로 업데이트(Update)**를 하도록 코드를 짰는데 업데이트할 대상이 없다며 에러가 나는 것이었다.

상황을 요약하면 대략 이렇다.
- `Service A`가 트랜잭션을 시작한다.
- `Service A`는 `Service B`를 호출한다.
- `Service B` 안에서 두 개의 트랜잭셔널 메서드를 순차적으로 호출한다.
  - `Service C` (또는 메서드 C): 데이터를 **Delete** 하고 새롭게 **Insert** 한다.
  - `Service D` (또는 메서드 D): 방금 Insert한 데이터를 찾아 **Update** 한다.

분명 코드 라인 상으로는 `Delete -> Insert -> Update` 순서로 완벽했다.  
C와 D 메서드 각각에 `@Transactional`도 달았으나 D에서 대상이 없다는 에러가 찍혔다.

---

## 2. 첫번째 원인: 하나의 거대한 트랜잭션 (Propagation.REQUIRED)

가장 먼저 든 생각은 *"C랑 D에 각각 `@Transactional`이 걸려있으니, C가 끝나면 DB에 커밋되고 D가 돌겠지?"* 라는 아주 순진한 착각이었다.

Spring의 `@Transactional`은 기본 전파 속성이 `Propagation.REQUIRED`이다. 
이 말은 즉슨, **이미 진행 중인 부모 트랜잭션이 있다면 새로운 트랜잭션을 만들지 않고 기존 트랜잭션에 합류(Participate)해 버린다**는 뜻이다.

1. `Service A`에서 트랜잭션 1번 시작.
2. `Service C`를 부를 때 1번 트랜잭션에 탑승.
3. `Service D`를 부를 때도 1번 트랜잭션에 탑승.

결국 C 메서드가 끝났다고 해서 DB에 쿼리가 커밋되거나 날아간 상태가 아니었던 것이다. 하나의 커다란 트랜잭션 덩어리 안에서 여전히 모든 작업이 **메모리(영속성 컨텍스트)**에만 머물러 대기중인 상태였다.

---

## 3. 두번째 원인: JPA (Hibernate)의 쓰기 지연과 Flush 순서

트랜잭션이 하나로 묶인 건 알겠다. 그럼 아직 커밋 전이어도 같은 트랜잭션 안이니까 내가 작동 시킨 순서대로 쿼리가 대기열에 쌓여서 잘 실행되어야 하지 않을까?
하지만 **JPA(Hibernate)의 지연 쓰기(Write-behind) 메커니즘**은 우리의 예상대로 정직하게 동작하지 않는다.

트랜잭션이 커밋될 때(또는 Flush가 일어날 때) 비로소 모아둔 쿼리를 DB로 날리는데, 이때 Hibernate는 **자기만의 고유한 쿼리 최적화 실행 순서**를 가지고 있다.

기본적으로 Hibernate 액션 큐(ActionQueue)의 DML 전송 순서는 다음과 같다.
1. **`Insert`** (EntityInsertAction)
2. **`Update`** (EntityUpdateAction)
3. **`Delete`** (EntityDeleteAction)

문제의 원인은 바로 여기 있었다.
 `Delete -> Insert -> Update` 순서로 코드를 짜고 이와 같은 순서로 작동할 것이라 예상했으나 , 트랜잭션이 하나로 묶여서 나중에 한 번에 Flush될 때 Hibernate는 위 규칙을 적용해서 **`Insert -> Update -> Delete` 순서로 쿼리를 재배열해서 날려버린 것**이다.

아직 DB에서 기존 데이터를 삭제하지도 않았는데 같은 PK/정보를 Insert 하려고 하니 제약조건이 꼬이고, 트랜잭션 내에서 지워질 예정으로 마크(mark)된 엔티티를 Update 하려 하니 영속성 컨텍스트가 꼬이면서 에러가 났던 것이다.

> 💡 **TMI: DML 순서를 임의로 바꾸는 이유?**  
> "아니 그냥 호출한 순서대로 쏴주면 안 되나?" 싶겠지만, Hibernate가 이렇게 쿼리를 모아서 재정렬하는 이유는 성능 최적화와 제약조건 충돌 방지를 위해서다. (예를 들어, 관계가 있는 테이블들을 다룰 때 참조 무결성(외래키 제약조건) 오류를 똑똑하게 피하기 위해 언제나 부모를 먼저 Insert 하고, 불필요한 연산을 줄이기 위함이다.)

## 4. 해결 방법

원인을 알았으니 해결책은 간단하다. 우리가 원하는 제어권(실행 순서)을 다시 가져오면 된다.

### 방법 1 - 물리적으로 다른 트랜잭션으로 강제 분리하기
`@Transactional(propagation = Propagation.REQUIRES_NEW)`를 사용하여 C와 D 메서드가 부모 트랜잭션에 합류하지 못하게 새로운 트랜잭션을 강제로 열어버릴 수 있다. 
이렇게 하면 C가 끝날 때 트랜잭션이 독립적으로 커밋되므로 `Delete -> Insert`가 DB에 그 즉시 확정되고, 이후 D가 완전히 새로운 트랜잭션으로 `Update`를 수행하게 되므로 문제가 발생하지 않는다. (단, 트랜잭션 커넥션이 그만큼 많이 소모된다는 단점은 유의해야 한다.)

### 방법 2 - 명시적 `flush()`, `clear()` 사용
큰 트랜잭션을 여러 개로 쪼개고 싶진 않다면, 순서가 꼬이지 않고 보장되어야 하는 시점에 강제로 `flush()`를 날려주면 된다.
`Service C`의 동작 로직 안에서, 혹은 `Service D` 로직을 시작하기 전에 `EntityManager.flush()` (Spring Data JPA라면 리포지토리의 `flush()` 또는 `saveAndFlush()`)를 호출하여 모여있는 쿼리를 즉시 DB에 쏴버리는 것이다. 
(필요하다면 1차 캐시를 비우는 `clear()`를 병행하여 영속성 컨텍스트를 깔끔하게 리셋할 수도 있다.)

---

## 마무리

1. 부모 트랜잭션이 열려있다면, 자식의 `@Transactional`은 기본적으로 새로운 커밋이나 Flush를 유발하지 않는다 (`Propagation.REQUIRED`).
2. JPA(Hibernate)는 트랜잭션 커밋 시 우리가 작성한 코드 순서가 아니라 **자체적인 규칙의 Flush 순서(`Insert -> Update -> Delete`)**에 따라 DB에 쿼리를 전송한다.

단순한 수정사항이었지만, 한번 더 생각하고 개발하지 않아서 발생한 문제였다..🥲  
늘 느끼지만, 개발자란 단순하게 현재 코드의 흐름만 보는 것이 아니라 전체적인 구조와 설계 그리고 동작 방식을 머릿속에 그려가며 개발해야한다고 생각한다.  
이런 경험으로 인해 테스트코드를 더 꼼꼼하게 작성해야겠다는 다짐과 함께 테스트 코드의 중요성을 다시 한번 느겼다.
