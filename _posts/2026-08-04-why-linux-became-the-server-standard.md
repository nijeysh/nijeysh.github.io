오늘 폐쇄망 환경에서 Windows Service의 `SYSTEM` 계정과 프로세스 권한 상속 문제로 하루 종일 문제 원인을 추적하면서 한 가지 질문이 꼬리를 물었다.

> *"Windows는 로그인 계정과 서비스 계정의 레지스트리(`HKCU`)가 다르고, Session 0 격리 같은 구조적 특성이 존재하는데... 이러한 OS 간의 차이가 서버 생태계의 지형을 바꾼 계기가 되었던 걸까?"*

단순히 "리눅스가 무료라서"라는 이유를 넘어, 두 OS가 지닌 물리적/구조적 차이점들을 팩트 위주로 정리해보고, 이러한 차이가 서버 환경에 어떤 영향을 미쳤을지 가설을 세워 정리해 본다.

---

## 1. 설정 관리 및 프로필 구조의 차이

두 OS는 시스템 설정을 다루는 방식에서 명확한 구조적 차이를 보인다.

### 1) Windows: 바이너리 기반의 레지스트리와 세션 분리
- **레지스트리 구조**: 사용자별 설정(`HKCU`)과 시스템 설정(`HKLM`)이 바이너리 파일 형태의 레지스트리로 관리된다.
- **프로필 격리 (Session 0)**: 서비스 프로세스가 구동되는 `SYSTEM` 계정은 일반 로그인 사용자의 레지스트리 및 프록시/인증서 프로필을 공유받지 못하고 `systemprofile`이라는 독립된 프로필을 사용한다.
- **특징**: 구동 계정 및 세션 격리에 따라 환경 설정과 레지스트리 참조 범위가 달라진다.

### 2) Linux: 텍스트 기반 파일 시스템과 단일 명세
- **"Everything is a File"**: 모든 설정, 네트워크 상태, 계정 정보가 `/etc/`, `/proc/` 아래의 **텍스트 파일**로 존재한다.
- **단일 명세**: 환경 변수와 권한(`UID`/`GID`, `rwx`) 규칙에 따라 동작하며, 텍스트 파일을 조회(`cat`, `grep`)하는 것만으로 현재 시스템 상태를 명확히 파악할 수 있다.

---

## 2. 프로세스 권한 및 격리 구조의 차이

### 1) Windows: SID 기반 Access Token 및 Session 격리
- 프로세스는 부모의 Security Context(AccessToken)를 상속받는다.
- 세션 0(서비스 영역)과 세션 1 이상(사용자 데스크톱 영역)이 물리적으로 분리되어 있어, 백그라운드 서비스가 사용자 세션의 자원에 접근하는 데 제약이 존재한다.

### 2) Linux: UID/GID 및 커널 단위 격리 (Namespaces / cgroups)
- 모든 프로세스는 `UID(User ID)`와 `GID(Group ID)`라는 단순한 식별자로 권한이 제어된다.
- 커널 차원에서 프로세스 공간을 쪼개주는 **`Namespaces`**(PID, Network, Mount 등)와 자원을 제한하는 **`cgroups`** 기술이 내장되어 있다.
- 훗날 이 커널 격리 기술을 응용하여 만들어진 대표적인 도구가 **Docker(도커)**이다.

---

## 3. 메모리 및 자원 점유 구조의 차이

- **Windows Server**: GUI 그래픽 서브시스템 및 백그라운드 관리 프로세스가 기본 구동되므로, OS 자체의 기본 메모리 점유(Base Footprint)가 수 GB 단위로 다소 무겁다.
- **Linux Server**: GUI가 존재하지 않는 **Headless CLI(Command Line Interface)** 상태로 동작하여 기본 OS 메모리 점유가 수십~수백 MB 수준으로 가볍다. 또한 남는 RAM을 동적 페이지 캐시(Page Cache)로 적극 활용하다가 애플리케이션이 요구할 때 즉시 해제해 주는 효율적인 메모리 관리 구조를 갖춘다.

---

## 4. 설정 제어 및 자동화(IaC) 방식의 차이

- **Windows**: GUI 마우스 제어 및 PowerShell 스크립트를 이용하며, 서비스 계정 권한이나 레지스트리 얽힘에 따라 자동화 구성 시 고려할 변수가 상대적으로 많다.
- **Linux**: 텍스트 파일 편집과 Shell 커맨드로 모든 제어가 가능하여, `Dockerfile`이나 `Shell Script` 몇 줄만으로 계정 생성, 권한 부여, 앱 구동 전 과정을 코드(Git)로 명시하고 자동화할 수 있다.

---

## 요약 / 결론

오늘 겪었던 윈도우 프로세스 권한 이슈를 계기로 두 OS의 구조적 차이점들을 팩트 위주로 짚어보았다.

1. **Windows**: 바이너리 레지스트리와 세션 분리(Session 0) 구조로 인해, 구동 계정에 따라 환경 설정과 레지스트리 참조 범위가 달라진다.
2. **Linux**: 텍스트 중심의 파일 시스템, 가벼운 CLI 자원 구조, `Namespaces/cgroups` 기반의 명확한 커널 단위 프로세스 격리 모델을 따른다.

개발 및 서버 운영 관점에서는 **설정의 투명성, 자원의 효율성, 코드 기반 배포 자동화(CI/CD, Docker)의 용이성** 측면에서 리눅스가 지닌 개발상의 우위 요소들이 명확했다.  
이러한 개발적 요소들이 복합적으로 작용하면서, 자연스럽게 리눅스가 백엔드 및 서버 생태계의 표준으로 자리잡은 것이 아닐까?
