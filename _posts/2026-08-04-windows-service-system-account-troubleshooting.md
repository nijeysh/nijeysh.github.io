고객사에 설치된 자사 솔루션이 폐쇄망 환경에서 원인을 알 수 없이 동작하지 않는 이슈가 발생했다.  
문제는 우리 솔루션이 내부 소스코드나 구체적인 동작 방식에 대한 인수인계 및 문서가 전무한 **'블랙박스(Black-box)' 상태**였다는 점이다.

개발자로서 디버거나 로그도 제대로 활용하기 힘든 폐쇄망 고객사 환경에서, A부터 Z까지 온갖 가설을 세워가며 하루 종일 노가다 추적을 거친 끝에 마침내 원인을 찾아냈다.

이 글은 소스코드 없는 환경에서 윈도우 프로세스의 **실행 주체(Execution Context)**와 **부모 프로세스 권한 상속** 원리를 이해하고 문제를 해결했던 트러블슈팅 기록이다.

---

## 1. 문제 증상: 똑같은 exe를 부르는데 결과가 다르다?

솔루션의 내부 호출 구조는 대략 다음과 같았다.

```text
[케이스 1 (실패 ❌)]
A (Tomcat WAR / Java) ──> B (exe) ──> C (원격 API/서버)  ==> C의 응답을 가져오지 못함 (통신 실패)

[케이스 2 (성공 ⭕)]
D (GUI 프로그램 / exe) ──> B (exe) ──> C (원격 API/서버)  ==> C의 응답을 정상 수신함
```

결국 최종 목적지인 `C`를 호출해서 응답을 받아와야 하는 핵심 로직은 모듈 `B.exe`가 담당하고 있었다.  
`B.exe`는 동일한 프로그램인데, **`A(Tomcat WAR)`에서 `B`를 호출할 때만 `C`의 응답을 가져오지 못하는 기이한 현상**이 발생했다.

---

## 2. 추적 과정과 결정적 힌트: 실행 계정 (User Name)

소스코드를 볼 수 없으니 모든 가능성을 가설로 세워야 했다.  
네트워크 망 차단 유무, 파라미터 전달 오류, 환경 변수 차이 등을 하나씩 확인하던 중 작업관리자(Task Manager)의 세부 정보 탭에서 결정적인 차이점을 발견했다.

바로 **프로세스를 실행하고 있는 윈도우 계정(User Name)**이 서로 달랐던 것이다!

- `A`가 실행한 `B.exe` ➔ **`SYSTEM`** 계정
- `D`가 실행한 `B.exe` ➔ **현재 로그인한 로컬 계정 (`User` / `Administrator`)**

---

## 3. 핵심 원리: 프로세스는 '실행 주체 (부모)'의 권한을 상속받는다

처음에는 `WAR(Java)`로 띄운 A와 `exe`로 띄운 D의 실행 파일 형태가 달라서 발생하는 문제인가 싶었다.  

하지만 OS 레벨에서 **명령어나 실행 파일 형태(`jar`냐 `exe`냐)는 실행 권한과 아무런 상관이 없었다.**  
핵심은 **"해당 프로세스를 띄운 부모 프로세스(실행 주체)가 누구인가"**였고, 프로세스는 부모의 **실행 계정(Security Context)**을 그대로 상속받는다는 지극히 기본적인 원리였다.

```text
[부모 프로세스 (실행 주체)]  ──(Process Spawn)──>  [자식 프로세스]
       (Security Context) ──────── 상속 ────────> (Security Context 동일)
```

### 💡 실행 주체에 따른 계정 차이

| 구분 | 실행 주체 (부모 프로세스) | `java.exe` 계정 | 자식 `B.exe` 계정 |
| :--- | :--- | :--- | :--- |
| **일반 실행** | 로그인한 사용자 (CMD / PowerShell / Explorer) | **`User` 계정** | **`User` 계정** |
| **서비스 실행** | Windows Service (`services.msc` / Background) | **`SYSTEM` 계정** | **`SYSTEM` 계정** |

### 1) `D.exe` (성공 케이스): 로컬 사용자 세션 상속
사용자가 윈도우에 로그인하여 Explorer(바탕화면)에서 `D.exe`를 직접 클릭하면, `D.exe`는 현재 로그인된 로컬 사용자 세션(`User`) 권한을 갖는다.  
따라서 `D.exe`가 연 `B.exe` 역시 **부모 프로세스 `D`의 `User` 권한을 상속**받아 정상 작동했다.

### 2) `A` (Java WAR / 실패 케이스): Windows Service 권한 상속
고객사 서버의 Tomcat(Java)은 윈도우 부팅 시 자동 실행되도록 **Windows 서비스(`services.msc`)**로 등록되어 있었다.  

Windows 서비스의 기본 실행 주체는 윈도우 최상위 시스템 계정인 **`NT AUTHORITY\SYSTEM` (SYSTEM)**이다.  
따라서 `Tomcat(Java VM)`이 `SYSTEM` 권한으로 켜졌고, Java 내부(`Runtime.getRuntime().exec()`, `ProcessBuilder`)에서 띄운 **`B.exe` 역시 부모인 Tomcat의 `SYSTEM` 계정 권한을 그대로 상속받은 것**이다.

## 4. 폐쇄망 환경에서 `SYSTEM` 계정은 왜 C 통신에 실패했을까?

"SYSTEM 계정이면 최고 권한인데 왜 네트워크 통신이 안 될까?"라는 의문이 들 수 있다.  
그러나 **폐쇄망 및 기업 내부망 환경**에서는 오히려 이 부분이 치명적인 함정이 된다.

1. **사용자 단위 레지스트리 및 프록시 설정 미적용 (`HKCU` vs `HKLM`)**: 폐쇄망 환경의 망연계/프록시(Proxy) 설정, 방화벽 규칙, CA 사설 인증서 등은 대부분 현재 로그인한 사용자 프로필(`HKEY_CURRENT_USER`)에 세팅되어 있다. 하지만 `SYSTEM` 계정은 독자적인 시스템 프로필(`C:\Windows\System32\config\systemprofile`)을 사용하므로 일반 사용자 계정의 프록시/망연계 설정을 공유받지 못한다.
2. **동기화의 한계**: 폐쇄망 특성상 인터넷이나 도메인 정책 동기화가 불가능하므로, `SYSTEM` 계정에 일반 사용자용 프록시/인증서 옵션을 일일이 동기화해 주는 조치는 현실적으로 불가능에 가깝다.
3. **네트워크 접근 권한 거부**: `SYSTEM` 계정으로 실행된 프로세스가 C 엔드포인트로 HTTP/Socket 요청을 보낼 때, 윈도우 네트워크 레이어에서 인증되지 않은 세션으로 판단되어 타임아웃이 나거나 응답이 차단된다.

---

## 5. 해결 방안

원인이 **"Tomcat 서비스의 실행 주체(로그인 계정) 문제"**였으므로 해결 방법은 명확했다.

1. `Win + R` ➔ `services.msc` (서비스 관리자) 실행
2. 설치된 **Apache Tomcat 서비스** 우클릭 ➔ [속성]
3. **[로그온] 탭** 이동
4. 기존 '로컬 시스템 계정(SYSTEM)'으로 설정된 것을 **'계정 지정'**으로 변경하여, C 통신 권한과 프록시 설정이 되어 있는 **실제 로컬 사용자 계정 정보** 입력 후 서비스 재시작

서비스 실행 주체를 변경하자, Java WAR에서 띄운 `B.exe`도 로컬 계정 권한을 상속받으면서 `C`와의 통신 및 응답 수신에 깔끔하게 성공했다.

---

## 요약 / 결론

1. 명령어나 실행 파일 형태(`jar`, `exe`) 자체는 OS 실행 권한을 결정하지 않으며, **프로세스는 오직 부모 프로세스의 실행 계정(Security Context)을 그대로 상속**받는다.
2. Windows 서비스(`services.msc`)로 구동된 Java/Tomcat은 기본적으로 `SYSTEM` 계정으로 켜지므로, 내부에서 띄우는 자식 프로세스 역시 `SYSTEM` 계정으로 구동된다.
3. 폐쇄망 환경에서는 `SYSTEM` 계정이 사용자 프로필(`HKCU`)의 프록시/인증서/방화벽 설정을 공유받지 못하므로, **서비스 실행 계정을 실제 권한이 있는 사용자 계정으로 지정**해야 네트워크 통신 장애를 방지할 수 있다.
