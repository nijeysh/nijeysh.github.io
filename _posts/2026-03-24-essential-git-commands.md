다들 업무 중에 브랜치에 잘못 커밋해서 되돌려야하는 상황을 겪어보았을 것이다. (나 또한 오늘 경험했다.. 식은땀이.. 😰)   
종종 쓰는 git 명령어인데 매번 검색해서 찾기도 귀찮고, 정확한 옵션을 헷갈릴 때가 많다.  

이참에 평소 자주 사용하는 기본 명령어들부터, 알고 있으면 유용한 병합 명령어들, 그리고 주의해서 써야 할 강력한 명령어들까지 한 번 정리해 보려 한다.

## 1. 기본 저장소 동기화 명령어

### git remote
원격 저장소(Remote Repository)를 관리하는 명령어이다.
- `git remote -v`: 연결된 원격 저장소 목록과 URL을 표시한다.
- `git remote add <name> <url>`: 새로운 원격 저장소를 기존 로컬 저장소에 추가한다. 기본적으로 `<name>`은 `origin`을 주로 사용한다.

### git push
로컬 저장소의 커밋 내역(변경 사항)을 원격 저장소로 업로드(Push)한다.
- `git push <remote> <branch>`: 특정 브랜치(예: main)를 원격 저장소(예: origin)에 푸시한다.
- `git push -u origin main`: 원격 저장소의 main 브랜치를 기본 업스트림으로 설정(`-u` 또는 `--set-upstream`)하고 푸시한다. 이후에는 `git push`만 입력해도 동작한다.

### git pull
원격 저장소의 최신 변경 사항을 가져와 로컬 브랜치에 병합(Merge)한다. 내부적으로 `git fetch` (원격 저장소의 업데이트 사항 가져오기)와 `git merge`를 순차적으로 실행하는 것과 동일하다.
- `git pull origin main`: origin의 main 브랜치 내용을 가져와 현재 작업 중인 브랜치와 병합한다.

## 2. 브랜치 병합 관련 명령어

### git merge
다른 브랜치의 커밋들을 현재 브랜치에 합친다.
- `git merge <branch>`: 지정한 브랜치의 변경 이력을 현재 브랜치로 가져와 새로운 **Merge Commit**을 생성한다. 브랜치가 나뉘었다가 합쳐지는 시각적 분기점(히스토리)이 그대로 보존된다.

### git rebase
현재 브랜치의 베이스(Base)를 다른 브랜치의 최신 커밋으로 변경(Rebase)하여, 히스토리를 선형적으로 깔끔하게 유지할 때 사용한다. Merge는 병합 커밋이 남지만, Rebase는 브랜치 분기점 자체를 옮겨 병합 커밋 없이 하나로 이어지는 깔끔한 히스토리를 만든다.
- `git rebase main`: 현재 브랜치의 시작점을 main 브랜치의 꼬리로 변경한다. (공유된 커밋에 대해 수행하면 충돌 및 히스토리 꼬임이 발생할 수 있으므로 주의가 필요하다.)

## 3. 편리한 추가 기능 명령어

### git stash
작업 중이던 코드를 임시로 저장 공간(Stash)에 숨겨두고, 나중에 다시 꺼내올 수 있는 기능이다. 아직 커밋하기엔 이르지만 다른 브랜치로 긴급하게 넘어가서 작업해야 할 때 매우 유용하다.
- `git stash` 또는 `git stash push`: 현재 추적 중인 파일의 변경 사항(워킹 디렉토리)을 임시 저장한다.
- `git stash list`: 저장된 스태시 목록을 확인한다.
- `git stash pop`: 가장 최근에 임시 저장한 스태시를 불러오면서 목록에서 제거한다. (`git stash apply`는 내용을 불러오되 목록에 남겨둔다.)

### git squash (Rebase Interactive)
여러 개의 자잘한 커밋을 하나의 의미 있는 커밋으로 합치는 기능이다. 일반적으로 `rebase -i` 명령어를 통해 실행하며, 지저분한 작업 기록을 깔끔하게 정리해 Pull Request를 올릴 때 유용하다.
- `git rebase -i HEAD~3`: 최근 3개의 커밋을 합치거나 수정할 수 있는 편집 텍스트 창을 연다. 여기서 이전 커밋에 병합할 커밋 앞의 단어를 `pick`에서 `squash` (또는 `s`)로 텍스트를 변경하고 저장하면 합쳐진다.

## 4. 강력한(주의가 필요한) 명령어

### git push --force (-f) 와 --force-with-lease 
원격 저장소의 커밋 히스토리를 무시하고, 강제로 로컬 저장소의 상태로 원격 저장소를 덮어쓴다. 협업 시 다른 사람의 소중한 커밋 내역을 완전히 날려버릴 수 있으므로 권장하지 않는 명령어이다.

**주의점 및 권장 사항:**
잘못 올린 브랜치를 덮어씌울 때 `git push --force` 대신 **`git push --force-with-lease`**를 사용하는 것이 안전하다. 
이 옵션은 내가 모르는 사이 다른 팀원이 원격 브랜치에 커밋을 푸시했다면 강제 덮어쓰기를 멈추고 충돌을 방지해 준다.

### git checkout --orphan
부모 커밋(기존 히스토리)이 전혀 없는 완전히 독립적인 새로운 브랜치를 생성한다. 이 브랜치에서 생성되는 첫 커밋은 해당 브랜치의 새로운 루트(출발점)가 된다.

**사용 예시:**
- `git checkout --orphan <new-branch>`: 무 상태(히스토리가 없는 빈 상태)의 `<new-branch>`를 생성한다. 
- 기존 작업 내역을 이어받지 않기 때문에, 프로젝트의 소스코드가 아닌 문서화 전용 페이지나(github-pages 배포용 등) 완전히 새로운 맥락의 빌드 결과물 코드를 관리하기 위해 별도의 레파지토리 빈 공간을 만들 때 유용하게 쓰인다.

> 💡 **TMI: `--orphan` 브랜치 활용 경험담**  
> 이번에 사이드 프로젝트를 위해 git에 저장소를 생성하고 로컬에서 작업한 소스들을 커밋하려고 했는데, 저장소를 생성할때 gitignore나 README.md 파일을 추가하면 커밋 이력이 생성되어 원격 저장소의 첫 커밋이 된다.  
커밋 이력 관리가 지저분해지는 것을 방지하고자, 기존 히스토리를 이어받지 않고 완전히 깔끔한 새 공간을 만들기 위해 `--orphan` 옵션으로 초기화했는데 아주 유용했다!

## 마무리 (요약)
자주 쓰는 `pull`, `push` 같은 기본 동기화 명령어 외에도 상황에 맞춰 `rebase`, `stash` 같은 유용한 기능들을 손에 익히면 협업과 코드 관리가 훨씬 수월해진다.   
특히 이번에 겪었던 일처럼, `force` 나 `orphan` 같이 리포지토리의 이력에 큰 영향을 미치는 명령어는 그 특성과 부작용(예: `--force-with-lease` 이용)을 정확히 이해하고 사용해야 한다는 점을 다시 한번 깨달았다.   
(하지만 결국 가장 중요한 건 브랜치를 한번 더 확인하고 커밋하는 것이다...🤣)
